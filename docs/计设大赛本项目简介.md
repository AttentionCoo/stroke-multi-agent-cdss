# 🧠 多智能体深度检索脑卒中临床辅助决策支持系统 (CDSS)

## 一、项目定位与总体简介

本项目是一个面向**脑卒中（Stroke）临床急救与连续管理场景**的智能医疗辅助决策支持原型。系统以大语言模型为核心，融合**检索增强生成（RAG）、双轴矩阵多智能体推理（Multi-Agent System）与多模态医学知识库**，支持从患者急诊接入、症状/影像输入到辅助分析、结构化复核和患者档案更新的演示流程。

与传统通用问答系统不同，本项目并非只依赖模型参数记忆生成结果，而是以医学文献与临床指南为知识底座，通过 **LangGraph Agentic RAG 状态图**完成**患者记忆激活 → 病例结构化分析 → 检索任务规划 → 混合检索 → 证据质量评估与查询重写 → 专家独立意见 → 交叉质询 → 主持人共识 → 双重校验反思 → 结构化报告生成**。系统强调"**证据先行、过程可观察、结果需复核、时效可追踪**"，定位为需进一步临床验证的辅助决策原型。

### 核心设计理念

| 设计原则 | 具体体现 |
|:---|:---|
| **证据先行** | 通过本地指南知识库与 PubMed 检索为辅助分析提供可核对证据 |
| **过程透明** | SSE 流式输出可观察的分析阶段、证据引用与校验状态，不暴露内部思维链 |
| **结果复核** | 模型校验流程外叠加结构化预检查、医生复核和版本审计 |
| **时效管控** | 绿道工作区根据录入时间动态展示参考时间窗与 DNT 计时器 |

### 目标用户群体

- 👨‍⚕️ **临床医生与急诊团队**：辅助医生查阅脑卒中相关指南、整理急诊病例并动态追踪参考时间窗与 DNT；系统输出仅供复核，不能替代诊疗决定。
- 🎓 **医学教学与医学生（规划）**：后续可基于脱敏病例和审核记录建设数字病例与住培考评功能，当前版本尚未实现。
- 🩺 **患者持续健康管理**：支持个体化健康数据的动态整合与纵向分析，使 AI 能力从单次问答扩展到连续的二级预防与医疗随访过程。

本项目不仅是一个 AI 模型应用，更是一个融合前端交互、后端反应式流处理与分布式模型推理服务的完整系统，具备高并发、高扩展性与实际应用潜力，为构建真实的院内 CDSS 提供了可行的技术路径。

## 二、系统整体功能简介

本项目围绕医疗辅助分析场景，构建了智能问诊、结构化绿道、患者档案、医学知识和工程评测五个可演示模块。为保证比赛陈述与仓库证据一致，当前能力边界如下：

| 状态 | 能力 |
| --- | --- |
| **已实现** | 多智能体流式辅助分析、结构化绿道预评估、动态时间窗与 DNT、患者档案、文献学习、医生复核与审计、打印报告 |
| **原型验证** | FHIR R4 风格 Bundle 导出；尚未完成具体医院字段映射、术语绑定与互操作认证 |
| **规划中** | 离线语音录入、住培病例生成与考评、CDA 导出、HIS/PACS 生产对接 |

### （一）智能问诊与 AI 辅助分析模块（含急诊绿道）

该模块是系统的核心功能入口，主要通过 **SSE（Server-Sent Events）长连接** 实现流式交互：

- **结构化医学推理**：系统在接收到输入后，首先通过 `IntentNode` 进行意图分类（`consultation` / `knowledge` / `irrelevant`），再通过 `AnalysisNode` 提取结构化临床信息（人口学背景、时间轴、神经系统查体、生命体征、影像学闭环、实验室指标），最终结合多智能体推理生成结构化结果。
- **全维临床视角**：输出维度包括"最可能诊断及依据、解剖定位分析、病理机制解释、置信度评估以及需排除的重要诊断"等，高度贴近真实临床思维。系统强制执行**三步逻辑主线**：解剖定位（Localization）→ 病因定性（Qualitative classification）→ 病理机制整合（Mechanism Integration）。
- **时效动态追踪（急诊绿色通道模式）**：用户可在独立绿道工作区结构化录入最后正常时间、到院时间、生命体征、NIHSS、实验室和影像关键结论。界面动态展示 4.5 小时静脉溶栓参考窗口、24 小时取栓评估参考窗口与 DNT，并明确提示缺失字段和关键阈值风险。
- **流式交互体验**：系统支持流式输出，用户可以实时看到可观察的分析阶段、证据引用与校验状态；界面不展示或宣称暴露模型内部思维链。
- **医生复核闭环**：结构化评估可保存、修改和比较差异；医生可接受、退回修改或驳回，并留下理由与版本快照。存在关键风险或信息不完整时不能直接接受。

### （二）结构化绿道评估与交付模块

- **结构化安全预检查**：以后端确定性规则检查字段完整性、时间线、血压、血小板、INR、影像出血等关键信号。该模块位于模型推理流程之外，不改变现有大模型算法，也不输出治疗决定。
- **一键辅助分析**：将结构化字段整理为临床摘要后发送到现有多智能体流程，减少手工遗漏，模型图、节点、提示词与路由保持不变。
- **可交付结果**：支持打印评估报告和导出 FHIR R4 风格原型 Bundle；所有输出均保留“辅助参考、需医生复核”的边界。

### （三）患者管理与个体化分析模块

传统 AI 系统多限于单次随机交互，本项目引入了患者电子档案管理机制。

- **长期档案维护**：用于记录和维护患者基本信息、既往病史、用药史及医生备注等关键数据。后端通过 MyBatis-Plus 操作 MySQL 8.0 持久化存储。
- **动态上下文联动**：单次问诊结束后，后台通过 `ConversationSummaryService` 自动评估每轮对话的信息价值并更新至 `all_info` 上下文字段。后续多轮就诊自动结合历史记录进行个体化风险评估，实现真正的连续性健康管理。
- **结构化资料交付**：绿道评估可打印，并可导出 FHIR R4 风格原型 Bundle。CDA、院内术语映射以及 HIS 对接仍属于后续工作，不宣称可直接用于生产交换。

### （四）医学多模态知识学习与文献检索模块

该模块主要用于支持医学学习、科研支持、多模态联合推理与模型知识底座更新。

- **本地与在线双擎**：
  - **本地知识库**：内置 **12 篇**中国脑卒中相关权威指南与共识（如《中国急性缺血性卒中诊治指南2023》《中国重症卒中管理指南2024》《脑血管病防治指南（2024年版）》等），提供在线 PDF 预览（基于 `pdfjs-dist`）与结构化浏览。
  - **在线文献拓扑**：集成 `PubMedService`，通过 NCBI E-Utilities API 一键抓取最新外文高水平文献列表，按证据等级排序（Practice Guideline > Meta-Analysis > RCT > Review > Case Reports）。
- **RAG 强力支撑**：
  - **文档解析管线**：PDF 通过分块策略切分为语义完整的片段（chunk），同时保留原文来源与页码元数据。
  - **AI Batch QA 衍生引擎**：系统精读医疗 PDF 并自动批量衍生提炼高质量 `Q:A` 对（附带原文页码标签），大幅提升急诊场景下的 BM25 关键词检索召回率。采用批次合并策略（每 10 个 chunk 为一批）降低 API 调用次数。
  - **双路混合检索**：ChromaDB 向量语义检索（DashScope `text-embedding-v2` 嵌入）+ BM25 关键词精确检索双路并发，再经 `gte-rerank` 重排模型深度打分。
- **规划能力**：离线语音查房记录（ASR + NLP）尚未在当前版本实现，后续可作为结构化录入的补充入口。

### （五）工程测试与可复现评测模块

- **分层自动化测试**：覆盖前端结构化数据转换、后端评估领域规则、审核流程以及模型层现有架构兼容性。
- **离线评测运行器**：对冻结病例和预测结果检查必需信息、禁用表述、引用白名单，输出 JSON、Markdown 与 SHA-256 哈希，不调用或改动现有模型推理。
- **规划能力**：住培数字病例生成器和智能考评反馈尚未在当前版本实现。

> 💡 **功能整体协同说明**：绿道模块先完成结构化采集与确定性预检查，再将摘要交给现有多智能体模块辅助分析；患者档案提供上下文，医学知识模块提供证据，审核与评测模块负责人工把关和工程验证。最终临床决策始终由医生作出。

本项目采用前后端分离与模型服务独立部署的**三层架构**，将用户交互、业务逻辑与 AI 推理能力进行深度解耦。

┌───────────▼──────────────────────▼─────────────────────────┴──────────────┐
│               后端服务层 (Spring Boot 3.3 / WebFlux / Java 21)            │
│ ┌──────────────────┐  ┌────────────────────┐  ┌─────────────────────────┐ │

│ └─────────┬────────┘  └──────────┬─────────┘  └────────────▲────────────┘ │

### （一）前端交互层设计 (Frontend)

前端基于 **Vue 3.5 + Vite 7** 框架构建，采用组件化开发模式。

| 技术栈 | 版本 | 用途 |
|:---|:---:|:---|
| Vue | 3.5.x | 响应式 UI 框架 |
| Vite | 7.x | 构建工具与开发服务器 |
| Pinia | 3.x | 全局状态管理 |
| morphdom | — | 流式 HTML DOM diff 高效合并 |
| marked + DOMPurify | — | Markdown 安全渲染 |
| pdfjs-dist | — | PDF 在线预览 |
| SSE (EventSource) | — | AI 推理流式接收 |

- **核心功能**：实现智能问诊、患者管理、急诊倒计时与医学知识学习的统一展示。支持模块快速切换（`WorkspaceTabs`）、医学文档（PDF）在线预览（`PdfPreviewModal`）、语音录入、以及医学影像/检验报告图片的上传（支持拖拽与多图预览）。
- **流式与动态渲染**：重点实现了基于 `ReadableStream` 的流式数据接收机制，通过 `morphdom` 进行 DOM diff 高效合并，持续接收后端推送的分析结果并实时打字机渲染。同时，前端挂载基于 SSE 的实时动态时效面板，实时更新 DNT 和发病时间窗状态。

### （二）后端服务层设计 (Backend)

后端基于 **Spring Boot 3.3 / Java 21 / Spring WebFlux** 构建，负责高并发环境下的核心业务流转与医院系统对接。

| 技术栈 | 版本 | 用途 |
|:---|:---:|:---|
| Spring Boot | 3.3.13 | 应用框架 |
| JDK | 21 | 运行环境（虚拟线程支持） |
| Spring WebFlux | — | 响应式非阻塞 Web 框架 |
| MyBatis-Plus | 3.5.5 | ORM 持久层 |
| Redisson | — | 分布式锁 + 限流器 |
| HikariCP | — | 数据库连接池 |
| JWT + Spring Security | — | 认证与权限控制 |

- **安全与控制**：通过 JWT 机制（`TokenInterceptor`）实现医生/医学生身份认证与患者权限隔离，利用 `Redisson` 分布式锁与限流器控制急诊高并发环境下的读写冲突。
- **调度与中转**：采用响应式编程模型，通过 `WebClient` 对底层模型服务进行非阻塞的流式调用（`AIStreamingServiceImpl`），并将底层 Python 服务输出的事件流稳定转发至前端，实现端到端的高效数据链路。

### （三）模型推理服务层设计 (Model)

基于 **Python 3.11+ / FastAPI 0.128** 构建，是系统智能能力的核心大脑。

| 技术栈 | 版本 | 用途 |
|:---|:---:|:---|
| FastAPI | 0.128+ | 异步 Web 框架 |
| LangGraph | 0.2.20 | 状态机推理图编排 |
| LangChain | 0.3.x | LLM 调用与工具链 |
| DashScope SDK | — | 阿里云模型调用（Qwen 系列） |
| sse-starlette | — | SSE 流式输出 |
| ChromaDB | — | 向量数据库 |
| 离线评测运行器 | 项目内置 | 冻结输入、规则检查、哈希与报告归档 |

- **统一入口加载**：集成大语言模型（Qwen-Max / Qwen-Plus / Qwen-Turbo 三级模型矩阵）、多模态视觉模型（Qwen-VL-Max，通过 DashScope `MultiModalConversation` API 调用）、混合检索引擎（ChromaDB + BM25）、重排模型（gte-rerank）及 LangGraph 状态机推理模块。
- **异步流式输出**：通过异步生成器（`Async Generator`）持续输出 `thinking`（思考流）、`chunk`（文本流）、`done`（结束标志）等标准事件流，保持前后端一致的流式通信。

### （四）三层协同与架构优势

- **数据流向**：用户输入/影像上传 → 前端发送请求 → 后端处理与转发 → 模型服务推理 → 流式返回结果 → 前端实时渲染。
- **架构优势**：这种设计具备极高的可扩展性（可独立升级或替换 AI 模型）、高并发支持（响应式架构）、以及良好的工程落地性，为从开发环境到真实的院内生产部署（如 HIS/PACS 外挂挂载）铺平了道路。

## 四、核心技术与模型能力

本项目的核心竞争力在于其面向医疗场景深度定制的智能推理与安全拦截能力。

### （一）LangGraph Agentic RAG 状态机推理引擎

系统基于 **LangGraph StateGraph** 构建了带双循环的临床推理状态机：证据不足时进入查询重写与再次检索，校验未通过时重新进行专家会诊。

```text
Intent ─► Memory ─► Analysis ─► ResearchPlan ─► Retrieve ─► EvidenceJudge
  │                                                     ▲          │
  ├─ irrelevant ─► Reject                               └─ Rewrite ┘
  └─ knowledge ─► KnowledgeAnswer                                  │
                                                                  ▼
Report ◄─ Validate ◄─ Consensus ◄─ Debate ◄─ Reason（专家并行）
             │                              ▲
             └──────── retry ───────────────┘
```

| 节点 | 实现类 | 核心职责 | 使用模型 |
|:---|:---|:---|:---|
| IntentNode | `intent_node.py` | 意图三分类：`consultation` / `knowledge` / `irrelevant` | qwen-turbo |
| MemoryNode | `memory_node.py` | 激活短期、情景、语义三级患者记忆 | — |
| AnalysisNode | `analysis_node.py` | 结构化提取人口学、时间轴、查体、影像、实验室指标 | qwen-max |
| ResearchPlanNode | `research_node.py` | 检索任务拆分、医学查询扩展与 HyDE | qwen-plus |
| RetrieveNode | `retrieve_node.py` | ChromaDB + BM25 双路检索 → RRF → gte-rerank，生成证据编号 | — |
| EvidenceJudge / QueryRewrite | `evidence_node.py` | 评估证据充分性，不足时改写未检索过的查询 | qwen-plus |
| ReasonNode | `reason_node.py` | 三专家并行形成独立、带证据依据的初始意见 | qwen-max |
| Debate / Consensus | `debate_node.py` | 专家交叉质询，由中立主持人裁决分歧并生成共识 | qwen-max / qwen-plus |
| ValidateNode | `validate_node.py` | 规则引擎硬拦截 + LLM 软审查双重校验 | qwen-plus |
| ReportNode | `report_node.py` | 按 5 种模板生成结构化临床报告 + 安全卫栏 | qwen-max |

**状态数据模型（ClinicalState）**：除病例、提案和报告外，状态显式记录 `patient_memory`、`retrieval_queries`、`retrieval_round`、`evidence_quality`、`missing_information`、`expert_opinions`、`debate_transcript` 与 `consensus`，保证检索与协作过程可追溯。

### （二）检索增强生成（RAG）机制

系统以医学文献与临床指南作为知识底座，实施证据获取前置。

- **混合检索策略**：采用向量检索（ChromaDB）与 BM25 关键词检索并发，兼顾语义相似性与高频医学术语（如"TOAST分型"、"NIHSS评分"）的精确匹配。
- **指南优先策略**：针对脑卒中场景，优先返回权威指南（如 AHA/ASA 指南、中国脑卒中诊疗指南）与最新文献内容，从源头切断大模型"凭空捏造"的幻觉风险。
- **高级 QA 自建引擎**：系统精读医疗 PDF 并自动批量衍生提炼高质量 `Q:A` 对（附带原文页码标签），大幅提升急诊场景下的检索召回率。
- **主动检索规划**：模型先拆分临床任务，再生成中英文专业检索式、同义词扩展与 HyDE 医学描述。
- **Self-RAG 式证据评估**：每轮检索后评估相关性、可信度、时效性和覆盖度；证据不足时自动改写查询，默认最多两轮。
- **编号证据约束**：检索结果使用 `R{轮次}-Q{查询}-E{证据}` 编号，专家与主持人只能引用实际存在的证据编号。

### （三）证据重排与上下文优化

在初步召回文档后，系统引入重排模型（Reranker）进行深度语境打分与二次筛选。

- **语义重排**：集成 `gte-rerank` 重排模型，对混合检索召回的候选证据进行深度语境相关性打分与二次排序，精准计算指南片段与临床主诉的语义相关性。
- **上下文压缩**：通过限制证据长度并进行结构化聚合，避免冗余信息干扰模型推理效率，防止长上下文导致的"迷失在中间（Lost in the Middle）"现象。
- **溯源标注约束**：对模型声明采纳的证据要求附来源标注（包括文献名称、章节、页码）；实际覆盖率需通过冻结预测集评测，不预设为 100%。

### （四）医学多模态联合推理机制 (Multimodal)

在文本分析基础上，系统深度整合了视觉与语音的多模态能力。

- **ASPECTS 评分辅助提示**：通过多模态大模型（Qwen-VL-Max）对急诊头颅 CT 的高密度影、脑沟变浅等区域进行视觉语义理解，自动关联并辅助计算 ASPECTS 评分。
- **检验检查全景关联**：自动读取并解析患者的血小板计数、凝血功能（INR）等报告单图片，将异常指标转化为结构化文本，强制作为禁忌症审查因子的输入。
- **智能意图分流**：系统根据用户提问中的关键词自动识别影像类型（检验报告 / 药品识别 / 通用影像），加载对应的专科提示词模板，实现精准的多模态分析。

### （五）医学多智能体矩阵协同推理机制（Multi-Agent System）

为解决传统单模型医疗决策盲点多、风险高的痛点，系统基于 **LangGraph** 创新设计了"**业务专家轴（纵向） × 决策行为轴（横向）**"的双轴矩阵多智能体协同架构，模拟三甲医院真实临床的"科室会诊"与"三级把关"流程。

```text
                    【 决策行为轴 (横向 LangGraph 拓扑) 】
                    Independent           Debate             Consensus
                  (专家独立意见)       (交叉质询修正)       (主持人裁决)
                  ┌─────────────────┐ ┌───────────────┐  ┌────────────────┐
全科医生 (GP) ───►│ 整体病情与风险立场│ │ 阅读同伴意见  │  │ 已达成共识     │
神经专家 (NS) ───►│ 定位与时间窗立场  │ │ 质疑冲突判断  │──►│ Proposal       │
临床药师 (CP) ───►│ 禁忌证与用药立场  │ │ 修正专业结论  │  │ Critique       │
                  └─────────────────┘ └───────────────┘  └────────────────┘
                            ▲                                      │
                            └──────── [校验失败后重新会诊] ─────────┘
```

- **纵向（医学专家角色定义，由 `expert_config.yaml` 动态配置）**：
  - **全科医生 Agent**：负责全盘审视整体状态，提取主诉、既往史与慢病风险。配置于 `expert_config.yaml` 的 `generalist` 角色。
  - **神经专科医生 Agent**：核心决策大脑，专注于特异性表现、NIHSS 评分、CT/MRI 多模态影像特征（ASPECTS评分）及溶栓/取栓时间窗硬管控。配置于 `specialist` 角色。
  - **临床药师 Agent**：侧重用药安全，审查检验报告单（如 INR、血小板），严审绝对/相对禁忌症及配伍风险。配置于 `pharmacist` 角色。

- **横向（Independent-Debate-Consensus 拓扑）**：
  - **Independent（独立意见）**：三大专家通过 `asyncio.gather` 并行产出初始专业立场，关键医学判断引用实际证据编号。
  - **Debate（交叉质询）**：每位专家阅读全部同伴意见，明确同意点、冲突点、修正结论和需人工确认的不确定性。
  - **Consensus（主持人共识）**：中立主持人裁决分歧，分别输出共识、综合提案和风险批判；再由 `ValidateNode` 执行双重纵深防御：
    - **第一层：规则引擎硬拦截**（`rules_config.yaml`）——基于确定性规则检查绝对禁忌症（如 INR > 1.7、血小板 < 100×10⁹/L、3 个月内颅内出血史等），一旦命中立即标记为 `hard_violation`，不可绕过。
    - **第二层：LLM 软审查**——通过 qwen-plus 对提案进行语义级风险审查，识别规则引擎无法覆盖的隐含风险。
  - **动态反思自愈循环**：若校验结果为 `retry`（存在可修正问题），`ValidateNode` 将状态回传至 `ReasonNode` 重新推理；若多次重试仍失败（`fail`），则强制输出报告并附带醒目安全警告。

### （六）结构化报告生成与安全卫栏

`ReportNode` 根据 `report_templates.yaml` 配置，支持 **5 种报告模式**（标准会诊报告、急诊绿道报告、知识问答、教学病例分析、通用分析），每种模板包含固定的章节结构与安全卫栏：

- **安全卫栏（Guardrails）**：报告末尾强制附加"⚠️ 安全提示"模块，包含禁忌症检查结果、置信度声明与免责声明。
- **证据溯源块**：报告模板要求诊断建议附检索来源（文献名 + 章节 + 页码）；缺失引用会在离线评测中标记。

### （七）流式分析与自动评测机制

- **Token 聚合机制**：通过 SSE 协议将可观察的阶段事件和模型文本逐步传递至前端，并对高频输出进行合并处理，减少长文本报告生成时的渲染压力。
- **可复现离线评测**：通过冻结病例和预测文件，对必需信息、禁用表述和引用白名单进行规则检查，同时记录文件哈希。该运行器不调用大模型，不改变现有推理流程。

### （八）三级模型矩阵与算力分级策略

系统针对不同推理节点的精度与速度需求，部署了三级模型矩阵，实现算力与成本的精细化管理：

| 模型层级 | 模型实例 | 部署节点 | 设计考量 |
| --- | --- | --- | --- |
| **旗舰级** | Qwen-Max | 专家独立意见、交叉质询、报告生成 | 高参数模型确保专业立场与多方质询深度 |
| **均衡级** | Qwen-Plus | 检索规划、证据评估、查询重写、主持人共识、质控 | 兼顾推理精度与响应速度，控制证据和安全环节延迟 |
| **极速级** | Qwen-Turbo | 意图识别、极速通道问答、命名模型 | 极低延迟响应，支撑高并发轻量级任务 |

## 五、创新点与作品亮点

- 🏆 **(一) 证据驱动的医学推理范式创新**：打破传统大模型"先生成再解释"导致的严重医疗幻觉，将证据获取前置。模型在生成答案前必须依赖外部多模态医学知识，实现了从"模型主导"向"证据主导"的范式跨越。系统内置 **12 篇**权威指南 + PubMed 实时文献检索 + AI Batch QA 自动衍生引擎，构建了完整的医学知识底座。
- 🛡️ **(二) 多智能体协同的安全拦截机制**：采用“独立意见—交叉质询—主持人共识”协作架构，配合 **ValidateNode 双重纵深防御**（规则引擎硬拦截 `rules_config.yaml` + LLM 软审查）与 **LangGraph 会诊反思循环**，形成“证据检索 → 多方质询 → 共识裁决 → 拦截修正”的安全闭环。
- ⏱️ **(三) 结构化绿道路径设计**：将"时间就是大脑"的临床理念工程化，引入动态参考时间窗、DNT 追踪、字段完整性和关键阈值预检查。用户可一键把结构化摘要发送到原有多智能体流程，但倒计时不会改变 Agent 算法或模型路由。
- ⚖️ **(四) 极速通道与安全通道双路径设计**：通用知识问答通过快速路径响应（IntentNode → KnowledgeAnswer）；面对高风险临床病例，系统进入 Agentic RAG、证据评估、多专家辩论和双重校验完整路径，兼顾效率与医疗安全。
- 🔄 **(五) LangGraph 状态机驱动的新一代编排架构**：摒弃传统线性 if-else 链式调用，采用 LangGraph StateGraph 实现声明式状态机定义。支持意图分流、三专家并行、证据不足重检索和校验失败重会诊两类有界循环，使推理流程具备**可视化、可调试、可扩展**的特性。
- 🧠 **(六) 面向连续诊疗的三级患者记忆**：将当前对话、历史健康事件、稳定病史分别组织为短期、情景、语义记忆；加载前校验医生与患者归属，并将对话固定绑定单一患者，切换患者时要求新建对话，避免病历串联。
- 🔄 **(七) 采集、推理、复核与审计闭环**：结构化绿道提供输入和预检查，知识库提供证据，多智能体提供辅助分析，医生复核与版本快照提供人工把关和可追溯性。
- 💻 **(八) 工程化与可扩展性的模块设计**：提示词、报告模板、校验规则和模型调度沿用原有配置；新增评估领域模块通过窄接口隔离规则、持久化和 FHIR 原型导出，便于独立测试与后续适配。

## 六、应用价值与落地前景

- 🏥 **临床辅助决策支持（CDSS 原型基础）**：为急诊和基层医生集中展示时间窗、缺失数据、关键风险信号和证据引用，支持更高效的核对与复核。接入 HIS/PACS 前仍需完成院内适配、安全评估和临床验证。
- 🎓 **医学教学与培训支持（规划）**：现有结构化病例与审计记录可为后续住培病例生成和考评提供数据基础，数字病例生成器尚未在当前版本实现。
- 👨‍👩‍👧‍👦 **患者管理与长期健康服务**：通过 `ConversationSummaryService` 实现跨轮次对话上下文自动摘要与 `all_info` 动态更新，支持卒中后的二级预防、慢病随访、康复跟踪、依从性管理及长期风险干预。
- 🔬 **医学科研与文献支持**：`PubMedService` 通过 NCBI E-Utilities API 辅助科研人员快速定位最新前沿研究，按证据等级排序梳理指南脉络，利用语义整合提高课题开展与综述撰写的效率。
- 🚀 **可扩展性与推广前景**：得益于优秀的模块化架构与"双轴矩阵"设计，所有专家角色、提示词模板、校验规则、报告模板均通过 YAML 配置文件动态管理，系统具备极强的多模态延展性和跨科室推广能力（如心血管、肿瘤等），为智能医疗系统从实验室走向真实院线环境提供了极具参考价值的落地范本。

## 七、可复现评测与效果验证

当前版本提供三层可验证证据：前端单元测试、后端结构化评估/审核领域测试、模型层架构兼容测试。另提供 `model/app/evaluation/benchmark.py` 离线运行器与 6 个合成边界病例，可检查必需信息、禁用表述、引用白名单，并输出机器可读结果、Markdown 摘要和 SHA-256 哈希。

当前仓库未包含可追溯的专家盲评原始记录、冻结预测全集或 RAGAS 结果文件，因此不声明诊断准确率、零漏报率、方案实用性或忠实度等精确临床指标。正式比赛评测建议按以下流程补齐：冻结脱敏病例集与模型版本，双人独立标注，记录分歧仲裁，运行评测脚本，再由临床专家对结果进行盲评并归档签字记录。

> 评测运行器仅用于工程质量与结果一致性检查，不等同于医疗器械临床评价，也不能证明系统临床有效性。
