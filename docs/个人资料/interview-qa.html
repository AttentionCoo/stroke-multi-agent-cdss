Q1

你的系统采用了"前层-中层-后层"三层架构，为什么这样分层？每层的核心职责是什么？

▾

答：

分层动机是模拟真实医院的多学科会诊流程，同时实现关注点分离——不同层有不同的容错要求和延迟容忍度：

层次节点链核心职责容错策略
前层intent→memory→analysis→research_plan→evidence_router→retrieve→evidence_judge信息收集与证据检索：识别意图、激活患者记忆、结构化病例、规划检索、路由证据源、执行检索、评估证据质量检索失败可降级（规则兜底），不阻塞流程

Q2

为什么选择 LangGraph 图编排而非简单的链式调用（Chain）？图编排带来了哪些具体优势？

▾

答：

链式调用（Chain）是线性 A→B→C，无法表达本项目需要的四种非线性模式：

Q3

ClinicalState 用 TypedDict 而非 Pydantic BaseModel 定义，为什么？

▾

答：

这是 LangGraph 框架的硬性要求：

  • 状态通道与 Reducer：LangGraph 用 Annotated[type, reducer_func] 声明字段合并策略。如 Annotated[list, operator.add] 表示多节点返回的 list 自动拼接。TypedDict 天然支持这种注解。
  • 部分更新语义：每个节点的 run() 返回部分状态更新字典，LangGraph 自动与当前状态合并。TypedDict 是轻量字典，天然支持"只写变更字段"。
  • Pydantic 的角色：用于节点内部的结构化输出（如 EvidenceRoutes、IntentResult），通过 llm.with_structured_output(schema) 约束 LLM 输出格式。这是与"图级别状态流转"不同层次。
代码依据：schema.py:36-89 的 ClinicalState(TypedDict)，对比 schemas.py 中 EvidenceRoutes(BaseModel)。

Q4

DebateNode 中如果某个专家 LLM 调用超时或报错，系统如何保证不拖垮整轮质询？

▾

答：

关键在 asyncio.gather(*tasks, return_exceptions=True)：

tasks = [self._challenge(expert, state, opinions) for expert in self.experts]
responses = await asyncio.gather(*tasks, return_exceptions=True)
  • return_exceptions=True：当某个 _challenge 抛异常时，不在 gather 层面传播，而是把异常对象作为该位置的返回值。其他专家继续正常完成。
  • 异常降级处理：遍历 zip(self.experts, responses) 时检查 isinstance(response, Exception)，异常则降级为占位文本 "未能完成本轮交叉质询。"。
  • 设计权衡：医疗场景中 3 个专家有 1 个超时，剩下 2 个的有效质询仍有价值。如果用 return_exceptions=False，一个失败会导致所有质询结果丢失。
代码依据：debate_node.py:33-48。

Q6

答：

三、RAG 检索与知识管理Q7 – Q9

Q7

RRF（Reciprocal Rank Fusion）的原理，为什么比简单分数归一化更适合融合异构检索器？

▾

答：

RRF 公式：

score(d) = Σ 1 / (k + ranki(d))

对每路检索结果按排名位置赋分：排名第 1 得 1/(k+1)，第 2 得 1/(k+2)。跨路累加后降序。k=60 是常用平滑常数。

为什么优于分数归一化：

  1. 消除量纲差异：向量余弦相似度（-1~1）与 BM25 分数（0~∞）量纲不同。RRF 只依赖排名，天然消除量纲。
  2. 对异常分鲁棒：BM25 极端高分不影响 RRF 融合。
  3. "多路共识"语义：向量排第 3、BM25 排第 2 的文档 RRF = 1/63+1/62≈0.032；只在向量排第 1 的 RRF = 1/61≈0.016。前者胜出。
代码依据：retrievers.py:327-345 的 _rrf_merge。

Q9

_clean_bm25_query 为什么要剥离布尔语法？PICO 式检索式对 BM25 和向量检索分别有什么影响？

▾

答：

PICO 检索式如：("mca" OR "middle cerebral artery") AND thrombectomy

  • 对向量检索：Embedding 理解语义，引号括号不影响编码，反而有助于精确表达意图。
  • 对 BM25：词袋模型，text.lower().split() 空白分词，"mca" 变成 ["\"mca\""] 而非 ["mca"]，与索引无法匹配。

cleaned = re.sub(r'["()]', ' ', query)                    # 去除引号/括号
cleaned = re.sub(r'\s+(?:AND|OR|NOT)\s+', ' ', cleaned)   # 去除独立布尔连接词
注意：只剥离前后有空白的 AND/OR/NOT，避免误删 OR=1.5, 95%CI 中的 OR。

6.1 Python 异步与并发机制 Q15 – Q18

Q15

ReasonNode 的 asyncio.gather 没有 return_exceptions=True，DebateNode 传了，为什么？

▾

答：

  • ReasonNode（reason_node.py:184）：asyncio.gather(*tasks) 无 return_exceptions。但 _ask_expert 内部有 try/except（reason_node.py:237-249），失败时返回 "未能获取{role}的意见"，不会抛异常。
  • DebateNode（debate_node.py:37）：asyncio.gather(*tasks, return_exceptions=True)。因为 _challenge 内部没有 try/except，失败会抛异常。不传会导致整轮质询全丢。

本质：ReasonNode 容错内聚到子方法，DebateNode 容错外移到 gather 层面。两种方式都能工作，DebateNode 更简洁。

Q16

asyncio.gather vs asyncio.TaskGroup 的异常传播区别？

▾

特性gatherTaskGroup (3.11+)

Q17

astream_text 中的协程调度与事件循环？

▾

答：

所有协程都在同一个事件循环上调度。Python 的 asyncio 是单线程单事件循环模型：

  • llm.astream(messages) 返回异步生成器，内部 await 让出控制权
  • asyncio.gather 提交多个协程到当前事件循环，IO 等待时切换执行
  • 不存在"各自的事件循环"——除非显式 loop.run_in_executor

asyncio.run() 创建新事件循环并运行到完成。在 FastAPI 中所有 async def 端点已在事件循环中运行，不能再调 asyncio.run()。模块顶层调用会创建独立事件循环，这是 aiosqlite 问题的根源。

Q18

为什么 aiosqlite 不能在模块顶层创建连接？

▾

答：

aiosqlite 原理：

  1. 创建后台线程运行同步 sqlite3
  2. 通过 asyncio.Queue 在主事件循环和后台线程间通信
  3. 后台线程需知道哪个事件循环注册 queue 读取端

AsyncSqliteSaver.from_conn_string(path) 内部调 asyncio.get_running_loop() 绑定当前循环。

模块顶层调用时：asyncio.run() 创建临时循环运行后关闭，aiosqlite 绑定到已关闭循环，后续 FastAPI 中 await checkpointer.aput(...) 会抛 RuntimeError: Event loop is closed。

正确做法：在 FastAPI 的 lifespan 中调用 await open_checkpointer()（checkpoint.py:85-99）。

6.4 RAG 检索细节 Q27 – Q30

Q27

为什么向量检索用原始 query，BM25 用清洗后的？

▾

答：

清洗会丢失语义信息。PICO 式查询 ("mca" OR "middle cerebral artery") AND thrombectomy：

  • 向量用原始：Embedding 理解布尔语义，引号括号不影响编码。
  • 向量也用清洗后：丢失 OR 的"任一匹配"语义，embedding 偏向 AND 联合语义，降低召回。

▾

答：

HybridRetriever._cache（retrievers.py:395-405）：缓存单 Collection 结果，键 MD5(query + top_k + category_filter + evidence_type)，TTL 300 秒。

6.5 证据质量评估与检索循环 Q31 – Q33

Q31

启发式回退评分上限 0.60 恒低于阈值 0.65，为什么？

▾

答：

设计意图：LLM 评估失败时无法确认证据真的充分。仅知"有 N 条"，不知来源权威性、相关性、覆盖度。

min(0.60, 0.20 + evidence_count * 0.10)：

  • 0 条 → 0.20；4 条 → 0.60（上限）
  • 上限 0.60 < 阈值 0.65 → 必定触发重检

保守策略的代价：即使 10 条高质量证据也重检。医疗场景中"多检一轮"的成本远低于"基于未验证证据做错误决策"的风险。

Q32

Q35

\b vs lookaround 在中文文本中的差异？

▾

答：

Python \w 包含所有 Unicode 字母/数字（含中文字符），所以 \b 无法识别"中文→数字"边界。

身份证 110101199003076534 前是"号"字：

  • \b：号 和 1 都是 \w，无边界 → 漏匹配
  • (?<!\d)：号 不是数字 → 前瞻成功 → 正确匹配

总结：中文文本中 \b 失效，应用 (?<!\d) / (?!\d)。

Q36

脱敏规则顺序"先具体后宽泛"——日期先于身份证会怎样？

▾

答：

18 位身份证含 8 位出生日期 YYYYMMDD，如 110101199003076534 中的 19900307。

如果日期正则排在前面：

  1. 标准日期正则（带 -/年月 分隔符）不匹配，不误脱敏
  2. 但宽松正则（如 \d{8}）会匹配 19900307 脱敏为 110101[日期已脱敏]6534 → 身份证漏脱敏
  3. 更危险：_PHONE（11 位）排在前面时，19900307653 被手机号匹配 → 身份证漏脱敏

当前顺序：身份证(18) → 身份证(15)=手机号(11) → 银行卡(16-19) → ... → 日期。长模式优先。

Q40

round(value, 3) 解决了什么浮点精度问题？

▾

答：

RAGAS 指标是浮点数，可能因浮点误差产生噪声。例如基线 0.783，实际计算值 0.7829999999999999。

  • 不 round：0.7829999999999999 < 0.783 → True → 判定降级 ❌

难点 1：专家意见冲突时如何形成可靠共识？

  • 问题：3 位专家可能给出矛盾建议（如神内建议溶栓，药师指出禁忌症）
  • 解决：DebateNode 让每位专家阅读其他专家意见并交叉质询 → ConsensusNode 由主持人综合形成 consensus/proposal/critique 三段式输出 → ValidateNode 双层校验 → 不通过时反思循环重新推理

难点 2：LLM 输出不稳定如何保证系统鲁棒？

  • 问题：LLM 可能输出非法 JSON、遗漏字段、格式错误
  • 解决：三层降级——结构化输出 → 文本解析 → 规则兜底

难点 3：如何防止 AI 给出危险医疗建议？

  • 问题：LLM 可能虚构证据、遗漏禁忌症、给出绝对化断言
  • 解决：纵深防御——ValidateNode 规则+LLM 反思 → ComplianceNode PHI/绝对化断言/剂量扫描 → HITL 医生审批 → 免责声明留痕

8.1 LangChain vs LangGraph（最高频，几乎必问） Q61 – Q63

Q61

LangChain 和 LangGraph 的区别是什么？为什么选 LangGraph？

▾

面试官意图：考察你是否理解两个框架的抽象层级差异，而非只会背 API。

答：

LangChain 是上层组件库（Chain、Tool、Memory、Retriever），LangGraph 是底层执行引擎（StateGraph、Node、Edge、Checkpointer、interrupt）。不是二选一，而是不同抽象层级：

维度LangChain ChainLangGraph StateGraph
执行模型线性 A→B→C有向图 + 条件路由 + 循环
状态管理无显式状态，靠 Memory 拼接TypedDict State + Reducer 合并
循环/重试不支持add_conditional_edges 支持反思循环
人工介入无原生支持interrupt() 挂起 + resume 恢复
持久化无Checkpointer（SQLite/Postgres）断点续传
适用场景固定流程、单次任务多步推理、需循环/中断/状态持久化

我选 LangGraph 的原因：临床决策有三种非线性模式——意图三分支路由、校验不通过的反思循环、报告生成前的 HITL 医生审批。Chain 无法表达这些，必须用图编排。

面试官最爱追问的三个坑：
  1. "Chain 能不能实现循环？"——能，但需要手动写 while + 状态管理，本质上是在手写一个简陋的 StateGraph
  2. "LangGraph 能不用 LangChain 吗？"——能，LangGraph 可独立使用，但 LangChain 的 LLM/Tool/Retriever 抽象很方便
  3. "什么时候用 Chain 就够了？"——单次问答、简单 RAG、固定 pipeline
Q62

LangGraph 的 State 更新机制是怎样的？Reducer 是什么？

▾

面试官意图：考察你是否真正写过 StateGraph，而非只看过文档。

答：

核心机制：节点函数不直接修改 State，而是返回一个 diff 字典（只含修改字段），LangGraph 自动合并进当前 State。

合并方式由 Reducer 决定：

class ClinicalState(TypedDict):
    messages: Annotated[list, operator.add]   # Reducer: 列表追加
    reflection_count: int                      # 无 Reducer: 直接覆盖
    consensus: str                             # 无 Reducer: 直接覆盖
  • Annotated[list, operator.add]：多节点返回的 list 自动拼接（如 ReasonNode 返回 {"messages":[msg1]}，DebateNode 返回 {"messages":[msg2]}，最终 messages=[..., msg1, msg2]）
  • 无 Reducer 字段：last-write-wins（后写覆盖），如 reflection_count 由 ValidateNode 读取+加1+写回

常见坑：误给 int 字段加 Annotated[int, operator.add]，导致累加而非替换——反思次数会加速增长，循环提前终止。

Q63

LangGraph 的 interrupt 是什么？和 Python raise 有什么区别？

▾

面试官意图：考察你是否理解 HITL（Human-in-the-Loop）的实现原理。

答：

特性interrupt(payload)raise Exception
作用域LangGraph 图执行层面Python 函数层面
状态自动序列化完整 State 到 checkpointer不保存
恢复外部调 resume(decision) 从中断点继续无法恢复，流程终止
返回值decision = interrupt(question) 返回人工输入无

执行流程：

  1. _human_review_node 调用 interrupt({"question": "是否批准该方案？"})
  2. 图执行暂停，State 持久化到 SQLite
  3. 前端展示审批界面，医生点击"批准"或"驳回"
  4. 后端调用 /model/resume + Command(resume="approved")
  5. interrupt() 返回 "approved"，_human_review_node 继续执行

关键点：interrupt 不是异常，是协作式让出控制权——图知道自己停在哪，也知道怎么回来。

8.2 RAG 检索（大厂重点考） Q64 – Q68

Q64

什么是 RAG？它解决的核心问题是什么？

▾

答：

RAG（Retrieval-Augmented Generation）= 先检索外部知识，再让 LLM 基于检索结果生成回答。

解决三个核心问题：

  1. 知识时效性：LLM 训练数据有截止日期，无法回答最新指南（如 2024 年卒中取栓扩展到 24h 的更新）
  2. 私有数据访问：LLM 没有医院内部指南/专家共识，RAG 从本地知识库检索
  3. 可追溯性：每个判断都能引用具体证据编号（如【证据 R1-Q1-E1】），而非 LLM 的"黑箱记忆"

RAG vs 微调：RAG 是"查资料"——知识更新只需重建索引，无需重训模型；微调是"灌知识"——推理更自然但更新成本高、容易遗忘。

9.3 事件协议与高频追问 Q85 – Q86

Q85

你们定义了哪些 SSE 事件类型？如何做向后兼容？

▾

答：

  • token：增量文本
  • node_start / node_end：节点生命周期
  • status：整体进度或错误提示
  • final：完整结果（可选）

协议层用 event 字段区分类型；未知 event 前端忽略，保证旧客户端仍能消费新服务端的 token 流。

Q86

流式过程中客户端断线、服务端超时怎么处理？

▾

答：

  • 客户端：fetch 失败后按 thread_id 重连或走非流式 /model/result 拉取最终态。
  • 服务端：StreamingResponse 在客户端断开时取消生成器；图状态已由 checkpointer 按 thread 持久化，可 resume。
  • 超时：对单节点 LLM 调用设超时，失败走节点内降级逻辑，避免整条 SSE 挂死。
