一、架构设计Q1 – Q3

Q1

你的系统采用了"前层-中层-后层"三层架构，为什么这样分层？每层的核心职责是什么？

▾

答：

分层动机是模拟真实医院的多学科会诊流程，同时实现关注点分离——不同层有不同的容错要求和延迟容忍度：

层次 节点链 核心职责 容错策略
前层 intent → memory → analysis → research_plan → evidence_router → retrieve → evidence_judge 信息收集与证据检索：识别意图、激活患者记忆、结构化病例、规划检索、路由证据源、执行检索、评估证据质量 检索失败可降级（规则兜底），不阻塞流程
中层 reason → debate → consensus 多专家会诊：各专家独立出具意见、交叉质询、主持人综合共识 单专家失败降级为占位文本（return_exceptions=True），不拖垮整轮
后层 validate → compliance → human_review → report 安全校验与输出：规则引擎 + LLM 反思校验、PHI / 绝对化断言合规审计、医生人工复核、报告生成 校验异常默认放行，合规问题不阻断，由 HITL 兜底

关键设计权衡：前层是"信息管道"，允许降级和跳过；中层是"推理核心"，需要并行容错；后层是"安全守门"，宁可放过不可误杀（避免校验自身故障阻塞临床流程）。

代码依据： clinical_graph.py:1-50 的架构注释，以及 clinical_graph.py:167-230 中 add_edge / add_conditional_edges 的编排逻辑。
Q2

为什么选择 LangGraph 图编排而非简单的链式调用（Chain）？图编排带来了哪些具体优势？

▾

答：

链式调用（Chain）是线性 A→B→C，无法表达本项目需要的四种非线性模式：

  1. 条件路由：意图识别后三分支——consultation → 记忆 → 分析 → …、knowledge → 直接回答、irrelevant → 拒绝。 代码中用 add_conditional_edges("intent", self._route_intent, {...}) 实现。
  2. 反思循环：校验不通过时，validate 节点路由回 reason 重新会诊（最多 N 次），而非简单重试。 代码中 _route_validation 返回 "retry" → "reason"。
  3. 并行节点：DebateNode 中多个专家的交叉质询用 asyncio.gather 并行执行，图编排让这些并行逻辑自然嵌入流程。
  4. 中断点（HITL）：_human_review_node 中调用 langgraph.types.interrupt 挂起流程等待医生审批，审批后通过 /model/resume 恢复。这是 Chain 无法实现的状态挂起 / 恢复。
  5. 状态持久化：build_checkpointer() 创建 SQLite checkpointer，支持断点续传——流程中断后可从上次状态恢复继续执行。
代码依据： clinical_graph.py:215-230 的条件边编排， clinical_graph.py:345-380 的 HITL 中断点。
Q3

ClinicalState 用 TypedDict 而非 Pydantic BaseModel 定义，为什么？

▾

答：

这是 LangGraph 框架的硬性要求。LangGraph 的状态管理机制依赖 TypedDict：

  • 状态通道与 Reducer：LangGraph 用 Annotated[type, reducer_func] 声明字段的合并策略。例如 Annotated[list, operator.add] 表示多个节点返回的 list 自动拼接。TypedDict 天然支持这种注解，而 Pydantic BaseModel 的字段合并语义不同。
  • 部分更新语义：每个节点的 run() 方法返回部分状态更新字典（只包含该节点修改的字段），LangGraph 自动与当前状态合并。 TypedDict 是轻量字典，天然支持这种"只写变更字段"的模式；Pydantic 模型要求所有必填字段都有值，不适合做部分更新。
  • Pydantic 的角色：项目中 Pydantic 用在节点内部的结构化输出（如 EvidenceRoutes、IntentResult、ResearchPlanResult）， 通过 llm.with_structured_output(schema) 约束 LLM 输出格式。这是"节点输入 / 输出的数据校验"，与"图级别的状态流转"是两个不同层次。
代码依据： schema.py:36-89 的 ClinicalState(TypedDict) 定义， 对比 schemas.py 中 EvidenceRoutes(BaseModel) 等结构化输出 Schema。

二、多智能体与推理机制Q4 – Q6

Q4

DebateNode 中如果某个专家 LLM 调用超时或报错，系统如何保证不拖垮整轮质询？

▾

答：

关键在 asyncio.gather(*tasks, return_exceptions=True)：

tasks = [self._challenge(expert, state, opinions) for expert in self.experts]
responses = await asyncio.gather(*tasks, return_exceptions=True)
  • return_exceptions=True：当某个 _challenge 抛异常时，不在 gather 层面传播，而是把异常对象作为该位置的返回值。 其他专家的质询不受影响，继续正常完成。
  • 异常降级处理：后续遍历 zip(self.experts, responses) 时，检查 isinstance(response, Exception)， 如果是异常则降级为占位文本 "未能完成本轮交叉质询。"，而非让整个 DebateNode 崩溃。
  • 设计权衡：在医疗场景中，3 个专家有 1 个超时，剩下 2 个的有效质询仍有价值。如果用 return_exceptions=False（默认），一个专家失败会导致整个 gather 抛异常，所有专家的质询结果全部丢失——这在临床决策中是不可接受的。
代码依据： debate_node.py:33-48。
Q5

Evidence Router 为什么需要"结构化输出快路径 + 文本解析回退"的双路径？什么情况下结构化输出会失败？

▾

答：

快路径：llm.with_structured_output(EvidenceRoutes) 让 LLM 直接输出符合 Pydantic Schema 的 JSON，省去手写 JSON 解析的脆弱性。

回退的触发场景（任一即回退）：

  1. Provider 不支持：with_structured_output 方法不存在（hasattr 检查失败），或调用时抛异常 （如 OpenAI 旧模型不支持 JSON Schema 约束）。
  2. 校验失败：LLM 输出的 JSON 不符合 EvidenceRoutes 的 Pydantic 校验（如 evidence_type 不是合法枚举值）， ainvoke 抛 ValidationError。
  3. Mock / 测试环境：type(llm).__name__ == "Mock" 时直接返回 None，因为 Mock 对象的 with_structured_output 无真实语义。
  4. LLM 为 None：初始化时未传入 LLM。

回退路径：用 astream_text 流式生成原始文本，再通过 parse_json_output 手动提取 JSON。 如果连文本解析也失败，最终走 _normalize_routes 的规则兜底——按 EVIDENCE_TYPE_CATEGORIES 字典映射默认类别。

三层降级：结构化输出 → 文本解析 → 规则兜底，确保任何 LLM 配置下都能产出有效路由结果。
代码依据： evidence_router_node.py:76-110， base.py:47-62。
Q6

ValidateNode 的反思循环：触发条件、终止条件，以及为什么"异常情况下默认放行"？

▾

答：

触发条件：校验结果为"不通过"（规则引擎命中禁忌症 或 LLM 反思返回 REJECT），且 reflection_count < max_reflection_count。此时 _route_validation 返回 "retry"， 图路由回 reason 节点重新会诊，validation_feedback 随状态传递，reason 节点的提示词会消费该反馈。

终止条件（三选一先命中）：

  1. 校验通过（validation_passed = True）→ 路由到 "pass" → compliance → report
  2. 反思次数达上限（reflection_count >= max_reflection_count）→ 路由到 "fail" → 仍走 compliance → report（强制输出，附校验反馈供医生参考）
  3. HITL 驳回次数达 HITL_MAX_REJECTS 上限 → 强制生成报告

默认放行的原因：

except Exception as e:
    logger.error(f"[validate] Reflection 调用异常: {e}，默认放行")
    return {"validation_passed": True, "validation_feedback": ""}

这是安全兜底策略：校验节点自身的故障（LLM 超时、网络异常）不应阻塞整个临床流程。如果校验节点崩溃导致流程卡死， 医生连未校验的草稿都看不到，反而更危险。默认放行后，后续的 ComplianceNode 仍会做合规审计，HITL 人工复核仍是最后一道防线。

代码依据： validate_node.py:80-130， clinical_graph.py:215-230 的 _route_validation 映射。

三、RAG 检索与知识管理Q7 – Q9

Q7

RRF（Reciprocal Rank Fusion）的原理，为什么比简单分数归一化更适合融合异构检索器？

▾

答：

RRF 公式：

score(d) = Σ  1 / (k + ranki(d))

对每路检索结果，按排名位置赋分：排名第 1 得 1/(k+1)，排名第 2 得 1/(k+2)，以此类推。 跨路累加后按总分降序。k=60 是业界常用平滑常数。

为什么优于分数归一化：

  1. 消除量纲差异：向量检索返回余弦相似度（-1~1），BM25 返回 BM25 分数（0~∞），两者量纲完全不同。 分数归一化需要 Min-Max 或 Z-Score，但不同查询的分数分布不同，归一化不稳定。RRF 只依赖排名，天然消除量纲问题。
  2. 对异常分鲁棒：BM25 偶尔产生极端高分（如查询词恰好匹配罕见词），归一化后该文档会主导融合结果。 RRF 只看排名，单个检索器的分数异常不影响融合。
  3. "多路共识"语义：一个文档在向量路排第 3、BM25 路排第 2，RRF 分数 = 1/63 + 1/62 ≈ 0.032；另一个文档只在向量路排第 1、BM25 未召回，RRF = 1/61 ≈ 0.016。 前者胜出——多路都排名靠前的文档更可信。
代码依据： retrievers.py:327-345 的 _rrf_merge 方法。
Q8

5 个主题隔离 Collection 的好处与额外复杂度？

▾

答：

好处

  1. 检索精度提升：查询"大血管闭塞取栓适应证"时，只在 treatment_collection 中检索， 避免 anatomy_collection 中的解剖教材内容作为噪声混入结果。
  2. 分桶路由与 Evidence Router 协同：Evidence Router 判定 evidence_type=treatment → 只查 treatment_collection，物理隔离保证不会检索到无关主题的文档。
  3. 独立更新：新增治疗指南只需重建 treatment_collection，不影响其他 4 个 Collection 的索引。

额外复杂度

  1. 路由逻辑：需要 route_collection() 函数按 metadata（category / domain / subtopic）将 chunk 归属到正确的 Collection， 优先级链：教材 → anatomy、LLM domain → 对应 collection、subtopic → treatment/etiology/prevention、其余 → guideline。
  2. 跨 Collection 汇总：UnifiedSearchEngine 需要维护 5 个 HybridRetriever 实例， 检索时按路由决定查哪些 Collection，再跨 Collection 汇总后统一重排。
  3. 健康检查：需要 _check_store_health() 校验每个 Collection 的条数与分桶数是否一致， 防止"库空但服务正常"的静默故障。
  4. QA 对生成：每个 Collection 独立生成 QA 扩充对，QA 对需继承原 chunk 的 subtopic 标签以保证归属一致。

Q9

_clean_bm25_query 为什么要剥离布尔语法？PICO 式检索式对 BM25 和向量检索分别有什么影响？

▾

答：

问题根源：translate_query（查询翻译服务）生成的 PICO 式检索式如：

("mca" OR "middle cerebral artery") AND thrombectomy
  • 对向量检索：Embedding 模型能理解语义，PICO 语法中的引号、括号、AND/OR 被当作自然语言的一部分处理， 不影响语义编码，反而有助于精确表达检索意图。
  • 对 BM25：BM25 是词袋模型，_default_bm25_tokenize 做的是 text.lower().split()——空白分词。 引号 "、括号 () 会被当作字面 token，"mca" 变成 ["\"mca\""] 而非 ["mca"]， 导致与索引中的 mca 无法匹配，召回严重退化。

清洗策略：

cleaned = re.sub(r'["()]', ' ', query)                    # 去除引号 / 括号
cleaned = re.sub(r'\s+(?:AND|OR|NOT)\s+', ' ', cleaned)   # 去除独立布尔连接词
注意：只剥离前后有空白的 AND/OR/NOT，避免误删医学缩写如比值比 OR=1.5, 95%CI 中的 OR。
代码依据： retrievers.py:67-80。

四、安全合规与评测Q10 – Q12

Q10

ComplianceNode 为什么"非阻塞"——发现问题不阻断流程？安全如何兜底？

▾

答：

非阻塞的设计权衡：

  1. 合规检查自身可能误判：PHI 检测用正则匹配，可能把医学术语中的数字误报为身份证号 / 手机号 （如"NIHSS 评分 15 分"中的 15）。如果阻断，误报会导致正常流程被卡死。
  2. 绝对化断言检测的灰度：100% 在某些语境下是合理的（如"该患者 100% 符合溶栓标准"是口语化表述）， 不应直接阻断。
  3. 临床时效性：卒中是时间敏感性疾病（"时间就是大脑"），流程阻塞可能导致治疗延误， 风险远大于合规问题本身。

安全兜底的三层防线：

层级 机制 作用
1 审计留痕 compliance_audit 字段记录所有检测问题、时间戳，写入服务端日志，事后可追溯
2 HITL 人工复核 human_review 节点在报告生成前挂起，医生可看到合规问题并决定是否批准
3 免责声明 DISCLAIMER 附到审计记录，报告生成环节引用，明确"AI 辅助决策参考，不构成诊断或处方"
代码依据： compliance_node.py:1-30 的设计注释， compliance_node.py:50-80 的非阻塞逻辑。
Q11

为什么 faithfulness 只做软门禁？和 LLM-as-Judge 的局限性有什么关系？

▾

答：

硬门禁 vs 软门禁的区别：

指标 类型 基线值 阻塞 CI？
Recall@3硬0.783✅ 低于基线则 CI 失败
MRR硬0.757✅
NDCG@10硬0.763✅
Recall@10软0.817❌ 仅告警

Faithfulness 做软门禁的原因：

  2. 检索指标确定性高：Recall / MRR / NDCG 是纯数学计算，给定检索结果和标注即可精确计算，无随机性。 适合做硬门禁。
  3. 避免 CI 误报：如果 faithfulness 做硬门禁，LLM 评分的一次随机波动就可能阻塞 CI， 导致正常代码无法合并，严重影响开发效率。

Q12

工具注册表中两处脱敏的设计意图？遗漏会有什么安全风险？

▾

答：

第一处：patient_info 参数日志截断

log_args = {
    k: (str(v)[:60] + "…" if k == "patient_info" and len(str(v)) > 60 else v)
    for k, v in arguments.items()
}
logger.info(f"[tools] 调用工具 {name}, 参数: {log_args}")
  • 意图：patient_info 包含患者病史、查体、用药史等 PHI（受 HIPAA 保护）。 日志文件通常多个服务 / 人员可读，完整 PHI 写入日志 = 数据泄露。
  • 遗漏风险：日志泄露违反 HIPAA Safe Harbor 规则，可能导致法律追责、罚款 （HIPAA 违规罚款可达数百万美元）。

第二处：ValidationError 脱敏

if isinstance(e, ValidationError):
    brief = "; ".join(
        f"{'.'.join(str(p) for p in err.get('loc', []))}: {err.get('type', 'invalid')}"
        for err in e.errors()
    )
    error_msg = f"参数校验失败: {brief or str(e)}"
  • 意图：Pydantic 的 ValidationError 默认消息包含用户输入值 （如 patient_info='患者男68岁高血压糖尿病...'）。只保留字段路径（loc）和约束类型（type），不暴露输入值。
  • 遗漏风险：错误消息可能被 API 响应返回给前端、写入日志、进入监控系统，任何环节都可能泄露 PHI。

6.1 Python 异步与并发机制 Q15 – Q18

Q15

ReasonNode 的 asyncio.gather 没有 return_exceptions=True，DebateNode 传了，为什么？

▾

答：

  • ReasonNode（reason_node.py:184）：results = await asyncio.gather(*tasks)——没有 return_exceptions=True。如果某个专家的 _ask_expert 抛异常，gather 会在调用层面直接传播该异常， 整个 ReasonNode 的 run() 方法会抛异常，LangGraph 会将该节点标记为失败。 但实际上 _ask_expert 内部有 try/except 包裹（reason_node.py:237-249）， LLM 调用失败时返回 "未能获取{role}的意见" 字符串而非抛异常。所以 gather 拿到的每个 result 都是字符串，不会触发异常传播。
  • DebateNode（debate_node.py:37）：responses = await asyncio.gather(*tasks, return_exceptions=True)——传了 return_exceptions=True。因为 _challenge 方法内部没有 try/except，LLM 调用失败会直接抛异常。 如果不传 return_exceptions=True，一个专家失败会导致整个 gather 抛异常，所有专家的质询结果全部丢失。

设计差异的本质：ReasonNode 在子方法内部做了异常捕获（容错内聚），DebateNode 把容错外移到 gather 层面。 两种方式都能工作，但 DebateNode 的方式更简洁——不需要在每个 _challenge 里重复写 try/except。

Q17

astream_text 中的协程调度与事件循环？

▾

答：

所有协程都在同一个事件循环上调度。Python 的 asyncio 是单线程单事件循环模型：

  • llm.astream(messages) 返回一个异步生成器，内部通过 await 让出控制权给事件循环
  • asyncio.gather(*tasks) 把多个协程提交到当前事件循环，事件循环在 IO 等待时切换执行
  • 不存在"各自的事件循环"——除非显式用 loop.run_in_executor 跑到线程池

asyncio.run() 的作用是创建一个新的事件循环并运行直到完成。如果在 FastAPI 中（FastAPI 内部用 uvicorn 的事件循环）， 所有 async def 端点已经在事件循环中运行，不需要也不能再调用 asyncio.run()。 在模块顶层调用 asyncio.run() 会创建一个独立的事件循环，和 FastAPI 的事件循环无关——这是 aiosqlite 问题的根源。

Q18

为什么 aiosqlite 不能在模块顶层创建连接？

▾

答：

aiosqlite 的实现原理：

  1. 创建一个后台线程运行同步 sqlite3
  2. 通过 asyncio.Queue 在主事件循环和后台线程之间通信
  3. 后台线程需要知道哪个事件循环来注册 queue 的读取端

AsyncSqliteSaver.from_conn_string(path) 内部调用 aiosqlite.connect()，后者会调用 asyncio.get_running_loop() 获取当前正在运行的事件循环，并将连接绑定到该循环。

如果在模块顶层调用（如 checkpointer = asyncio.run(open_checkpointer())）：

  • asyncio.run() 创建一个临时事件循环，运行完毕后关闭
  • aiosqlite 的连接绑定到这个临时循环
  • FastAPI 的事件循环是另一个循环
  • 后续在 FastAPI 中 await checkpointer.aput(...) 时，aiosqlite 尝试在已关闭的临时循环上调度任务 → RuntimeError: Event loop is closed

正确做法：在 FastAPI 的 lifespan 上下文中调用 await open_checkpointer()， 此时 asyncio.get_running_loop() 返回的就是 FastAPI 的事件循环，连接绑定正确。 代码中正是这样做的（checkpoint.py:85-99）。

6.4 RAG 检索细节 Q27 – Q30

Q27

为什么向量检索用原始 query，BM25 用清洗后的？

▾

答：

不在两路都用清洗后 query 的原因：清洗会丢失语义信息。

PICO 式查询：("mca" OR "middle cerebral artery") AND thrombectomy

  • 向量检索用原始 query：Embedding 模型（如 text-embedding-v2）能理解布尔语法的语义—— "mca OR middle cerebral artery"的 embedding ≈ "大脑中动脉"的语义向量。引号和括号不影响语义编码。
  • 如果向量也用清洗后 query：mca middle cerebral artery thrombectomy—— 丢失了 OR 的"任一匹配"语义，embedding 可能偏向"mca AND middle cerebral artery AND thrombectomy"的联合语义， 降低对单独 "mca" 或单独 "middle cerebral artery" 的召回率。
  • BM25 用清洗后 query：BM25 是词袋模型，"mca" 和 mca 是不同 token， 清洗后统一为 mca，与索引中的 token 匹配。

总结：两路检索器的"语言理解能力"不同，需要不同的输入预处理——向量路保留语义语法，BM25 路清洗为纯词袋。

Q28

两层缓存的一致性问题？

▾

答：

HybridRetriever._cache（retrievers.py:395-405）：缓存单个 Collection 的检索结果， 键为 MD5(query + top_k + category_filter + evidence_type)，TTL 300 秒。

UnifiedSearchEngine._cache：缓存跨 Collection 汇总后的最终结果。

  2. 但实际上，向量库更新通常发生在服务启动时（build_multi_collection_vectorstores）， 运行期间不会增量更新，所以缓存不一致在当前架构下不太会发生

两层缓存是否冗余：不完全冗余——UnifiedSearchEngine 可能跨多个 Collection 汇总， 缓存键包含 Collection 路由信息；HybridRetriever 缓存单 Collection 结果，避免同一 Collection 被不同查询重复检索。 但确实增加了维护复杂度，可以考虑只保留一层。

  • 在高并发下，一个 Rerank 限流可能导致所有用户请求卡顿 1 秒

应该改为：

await asyncio.sleep(1)  # 异步 sleep，让出控制权给事件循环

但 rerank 方法当前是同步方法（def rerank，不是 async def），不能用 await。要修复需要：

  1. 将 rerank 改为 async def rerank
  2. 内部用 await asyncio.sleep(1)
  3. 所有调用方改为 await self.reranker.rerank(...)

当前代码中 HybridRetriever.search 调用 self.reranker.rerank(...) 是同步调用， 改为 async 需要一路传播 async。

6.5 证据质量评估与检索循环 Q31 – Q33

Q31

启发式回退评分上限 0.60 恒低于阈值 0.65，为什么？

▾

答：

设计意图：LLM 评估失败时，无法确认证据是否真的充分——仅知道"有 N 条证据"， 不知道来源是否权威、内容是否相关、是否覆盖关键问题。

min(0.60, 0.20 + evidence_count * 0.10) 的逻辑：

  • 0 条证据 → 0.20（基线分，表示"有病例但无证据"）
  • 4 条证据 → 0.60（上限，表示"证据数量够但质量未验证"）
  • 上限 0.60 < 阈值 0.65 → 必定触发重检

"检索到 10 条高质量证据但 LLM 评估失败"是否浪费？

是浪费，但这是保守策略的代价。替代方案：

  1. 放宽上限：min(0.70, ...) → 证据 ≥ 5 条时可能跳过重检，但可能放过低质量证据
  2. 混合策略：证据数 ≥ 阈值（如 6 条）时直接标记 is_sufficient=True，跳过 LLM 评估
  3. 当前选择的理由：在医疗场景中，"多检一轮"的成本远低于"基于未验证证据做出错误决策"的风险
Q32

max_rounds=2 时实际最多检索几轮？

▾

答：

retrieval_round 从 0 开始，can_retry = retrieval_round < self.max_rounds。

  • 第 0 轮（初始检索）：retrieve → evidence_judge，retrieval_round=0， can_retry = 0 < 2 = True
  • evidence_judge 判定不足 → query_rewrite → 第 1 轮检索：retrieve → evidence_judge， retrieval_round=1，can_retry = 1 < 2 = True
  • evidence_judge 再次判定不足 → query_rewrite → 第 2 轮检索：retrieve → evidence_judge， retrieval_round=2，can_retry = 2 < 2 = False → 不再重检

实际最多检索 3 轮（第 0、1、2 轮）。max_rounds=2 的语义是"最多重试 2 次"而非"最多检索 2 轮"。

但注意：retrieval_round 的递增逻辑在 RetrieveNode 中（每次检索 +1），如果 RetrieveNode 每次都递增， 则第 2 轮检索后 retrieval_round=2，can_retry=False，不再重检。总共 3 轮。

Q33

空查询终止机制防止了什么问题？

▾

答：

def _route_rewrite(self, state: ClinicalState) -> str:
    if state.get("need_retrieve") and state.get("retrieval_queries"):
        return "retrieve"
    return "reason"

防止的问题：

  1. 无限循环：如果 need_retrieve=True 但 retrieval_queries=[]， 不检查空查询 → 路由到 retrieve → RetrieveNode 拿到空查询 → 返回空证据 → evidence_judge 判定不足 → need_retrieve=True → query_rewrite → 又生成空查询 → 死循环
  2. 空检索浪费：RetrieveNode 对空查询列表做无用 LLM 调用或直接返回空结果，浪费 token 和延迟
  3. LLM 退化：QueryRewriteNode 的 LLM 可能因为证据缺口模糊而无法生成有效查询 （如 missing_information=["未知"]），返回 {"queries": []}。 空查询终止让流程优雅降级到 reason 节点，用已有证据推理。

6.6 安全与合规细节 Q34 – Q36

Q34

"绝对不能使用华法林"会被命中吗？

▾

答：

正则：re.compile(r"绝对(?!禁忌|适应)")

对"绝对不能使用华法林"的匹配过程：

  • 绝对 匹配到"绝对"
  • (?!禁忌|适应) 负向前瞻检查"绝对"后面是否是"禁忌"或"适应"
  • "绝对"后面是"不能"，不是"禁忌"也不是"适应"
  • → 负向前瞻成功，正则命中 ✅

"绝对不能使用华法林"应该被报告吗？

应该。"绝对不能"是绝对化断言——在医学中，很少有"绝对不能"的情况 （华法林在机械瓣膜患者中可能是必需的）。正确的表述应该是"在该患者当前情况下不建议使用华法林，因为..."。

但有一个灰度场景："绝对禁忌证：活动性内脏出血"——这里的"绝对"修饰"禁忌证"而非断言本身， 正则的 (?!禁忌) 正是为了排除这种情况。

Q35

\b vs lookaround 在中文文本中的差异？

▾

答：

Python re 中 \b 的定义：匹配 \w 和 \W 之间的边界， 而 \w = [a-zA-Z0-9_] 加上所有 Unicode 字母/数字（包括中文字符）。

误匹配例子：

身份证号 110101199003076534 前面是中文"号"字：

  • 用 \b：号 是 \w（中文字符），1 是 \w， \w 和 \w 之间没有边界 → \b 不匹配 → 漏匹配身份证号
  • 用 (?<!\d)：检查 1 前面是否不是数字，号 不是数字 → 前瞻成功 → 正确匹配

漏匹配例子：

手机号 13812345678 前面是中文"电"字：

  • 用 \b：电 是 \w，1 是 \w，没有边界 → 漏匹配
  • 用 (?<!\d)：电 不是数字 → 前瞻成功 → 正确匹配

总结：中文文本中，数字常紧跟中文字符，\b 因为中文字符属于 \w 而无法识别"中文→数字"的边界。(?<!\d) / (?!\d) 只关心数字边界，不受中文影响。

Q36

脱敏规则顺序"先具体后宽泛"——日期先于身份证会怎样？

▾

答：

18 位身份证号结构：6位地区码 + 8位出生日期(YYYYMMDD) + 4位顺序码 + 1位校验码

例如：110101199003076534，其中 19900307 是出生日期。

如果日期正则排在身份证前面：

  1. 日期正则 _FULL_DATE = re.compile(r"\d{4}[-/年.]\d{1,2}[-/月.]\d{1,2}日?") 不匹配 （身份证中没有 - / 年 / 月 分隔符）→ 不误脱敏
  2. 但如果有一个更宽松的日期正则（如 \d{8} 匹配连续 8 位数字），它会匹配身份证中的 19900307，将其脱敏为 110101[日期已脱敏]6534 → 后续身份证正则无法匹配残缺的字符串 → 身份证漏脱敏
  3. 更危险的情况：_PHONE（11 位手机号）如果排在身份证前面，19900307653（11 位连续数字） 会被手机号正则匹配 → 脱敏为 110101[手机号已脱敏]4 → 身份证漏脱敏

当前代码的顺序：身份证(18 位) → 身份证(15 位) = 手机号(11 位) → 银行卡(16-19 位) → ... → 日期。 长模式优先，确保最长匹配先被脱敏，短模式不会"截断"长模式。

Q40

round(value, 3) 解决了什么浮点精度问题？

▾

答：

问题：RAGAS 计算的指标值是浮点数，可能因浮点运算产生精度噪声。

例如：

  • 基线 recall_at_3 = 0.783（文档中写的是 3 位小数）
  • 实际计算值可能是 0.7829999999999999（浮点表示误差）

不 round 时：0.7829999999999999 < 0.783 → True → 判定为降级 ❌

round 到 3 位后：round(0.7829999999999999, 3) = 0.783 → 0.783 < 0.783 → False → 通过 ✅

本质：基线值本身是 3 位小数的展示值（如 0.783 而非 0.7826...）， round 到相同精度后比较，消除低于该精度的浮点噪声。只有真正的降级 （如从 0.783 降到 0.782）才会被检测到。

Q41

MemoryNode 三类记忆的截断上限为什么这样分配？

▾

答：

_SECTIONS = (
    ("short_term", "短期记忆", 2600),
    ("episodic", "情景记忆", 2200),
    ("semantic", "语义记忆", 1600),
)

短期记忆最长（2600）的原因：

  1. 信息密度最高：短期记忆存储当前对话中最近的患者信息（如本次入院的主诉、查体、影像结果）， 是本轮推理最直接依赖的上下文
  2. 时效性最强：急性卒中决策高度依赖本次发病的细节（发病时间、NIHSS 评分、CT 结果）， 这些都在短期记忆中
  3. 不可截断的部分最多：发病时间、到院时间、关键评分如果被截断，溶栓时间窗判断会出错

情景记忆被截断的影响：

情景记忆存储历史会诊记录和既往决策（如"上次会诊建议抗凝"）。超过 2200 字符被截断 → 丢失较早的会诊细节 → 下游 ReasonNode 可能不知道患者之前尝试过什么治疗，导致重复建议或遗漏重要的既往决策依据。 但相比短期记忆，情景记忆对当前急性期决策的影响较小。

语义记忆最短（1600）：语义记忆是通用医学知识（如"卒中定义"），这些信息在检索证据中可以补充，截断影响最小。

总预算：2600 + 2200 + 1600 = 6400 字符，控制在 LLM 上下文窗口的合理范围内 （避免 prompt 过长导致截断或成本过高）。

Q43

c = "".join(str(getattr(b, "text", "") or "") for b in c)
